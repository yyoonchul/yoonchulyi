## 📝 Detailed Notes

### 1. How I work with Agents

1. Choose capable models and judge output by results
   - Ball argues that using the newest, strongest available models is worth the cost when weaker models’ errors require repeated attempts.
   - He illustrates the tradeoff by asking whether a 50% cheaper but inconsistently less capable generalist is really a good bargain.
   - He is less concerned than before that generated code will inevitably make a codebase unmaintainable.
   - These are Ball’s October 2026 working judgments, rather than measured claims about every model or codebase.
2. Describe the desired outcome and expose the full workflow
   - Ball recommends prompting for what should be true, rather than prescribing each implementation step.
   - His example asks an agent to make a bytecode compiler and virtual machine twice as fast, with a clear end-state target.
   - Tool access reduces unsupported invention because agents can inspect and act on the actual environment.
   - He would let an agent run software end to end, inspect production logs, deploy, monitor rollout, release, change flags, and triage reports.
3. Give agents workflow tools and test accumulated knowledge
   - Ball describes custom plugins for handling bug reports, contacting users, checking system health, and granting feature flags.
   - He identifies AGENTS.md files, skills, scripts, and documentation as knowledge that may accumulate in a codebase.
   - To see whether agents use that knowledge, he proposes a controlled comparison: send five agents in without guidance and compare control and treatment groups.
   - He argues agents are well suited to running such experiments, so teams can test whether instructions help instead of assuming they do.
4. Delegate iteration and ask for evidence
   - Rather than trying one change at a time in conversation, Ball suggests asking an agent to build tools that explore alternatives.
   - For example, generate 20 variations and a page for combining and testing them, or investigate four possible causes of a slowdown.
   - He calls for evidence such as end-to-end walkthroughs, demo videos, and before-and-after measurements.
   - Teams need to build judgment about what counts as evidence; he recommends explicitly saying that unsupported claims are not evidence in AGENTS.md.
5. Delegate asynchronously, preserve context, and focus human review
   - Ball recommends giving agents larger tasks and batching requests, with scheduled follow-ups such as checking logs in two hours or checking a service every morning.
   - He advises against manually tracking context-window usage; compaction can support threads ranging from a few messages to thousands.
   - In Amp, task threads linked to Git commits act as shared company memory, helping explain past decisions and avoid duplicated work.
   - He limits human review to high-impact files and changes, expects end-to-end tests, and judges work by whether it functions, is understandable, and can be changed later; local resource conflicts remain a practical obstacle.

- 에이전트가 축적된 지식을 실제로 활용하는지 실험하고, 반복 작업은 도구에 맡기며, 구체적인 증거를 요구하고, 더 큰 일을 비동기적으로 맡기라고 제안한다.
- 에이전트 대화 기록을 조직의 기억으로 활용하고 자동화와 예약 실행을 적극 도입하며, 사람의 코드 검토는 영향이 큰 파일과 변경에 집중하라고 말한다.

---

## 📝 상세 정리

### 1. 에이전트와 일하는 방법 (How I work with Agents)

1. 성능이 뛰어난 모델을 고르고 결과로 판단한다
   - Ball은 성능이 낮은 모델의 오류를 만회하느라 여러 번 다시 시도해야 한다면, 최신 고성능 모델을 쓰는 편이 비용을 감수할 만하다고 주장한다.
   - 비용이 50% 저렴하지만 일관성 없이 더 부족한 범용 모델이 실제로 이득인지 질문하며 비용과 능력의 절충을 짚는다.
   - 생성된 코드가 결국 코드베이스를 유지보수 불가능하게 만들 것이라는 우려는 예전보다 덜 중요하게 본다.
   - 이는 2026년 10월 현재 Ball의 실무 판단이며, 모든 모델과 코드베이스에서 검증된 보편적 결론은 아니다.
2. 원하는 결과를 설명하고 전체 작업 흐름을 보여준다
   - Ball은 구현 절차를 일일이 지정하기보다 최종적으로 무엇이 달라져야 하는지 지시하라고 권한다.
   - 예로 바이트코드 컴파일러와 가상 머신을 두 배 빠르게 만들라는 목표를 제시한다.
   - 도구 접근 권한은 에이전트가 실제 환경을 살피고 조작하게 해 근거 없는 추측을 줄인다.
   - 에이전트가 프로그램을 처음부터 끝까지 실행하고, 운영 로그를 확인하고, 배포와 출시를 진행하며, 배포 상태와 기능 설정을 살피고, 버그 신고를 분류하게 하자는 제안이다.
3. 작업 도구를 제공하고 축적된 지식을 검증한다
   - Ball은 버그 신고 처리, 사용자 연락, 시스템 상태 확인, 기능 플래그 부여를 위한 맞춤형 플러그인을 소개한다.
   - 코드베이스에는 AGENTS.md 파일, 기술, 스크립트, 문서 같은 지식이 쌓일 수 있다.
   - 에이전트가 그 지식을 활용하는지 확인하기 위해, 별도 안내 없이 다섯 에이전트를 실행하고 대조군과 실험군을 비교하는 방법을 제안한다.
   - 에이전트는 이런 실험을 수행하는 데 적합하므로, 지침이 효과가 있다고 미리 가정하지 말고 실제로 시험해 볼 수 있다는 주장이다.
4. 반복 탐색을 맡기고 증거를 요구한다
   - 대화에서 변경을 하나씩 시도하는 대신, 여러 대안을 탐색하는 도구를 에이전트가 만들도록 하라고 제안한다.
   - 예를 들어 20가지 변형을 만든 뒤 조합과 시험을 할 수 있는 페이지를 만들거나, 성능 저하의 원인 후보 네 가지를 조사하게 할 수 있다.
   - 처음부터 끝까지 진행한 시연, 데모 영상, 변경 전후 측정값처럼 확인 가능한 증거를 요구한다.
   - 무엇을 증거로 인정할지 팀이 판단력을 길러야 하며, AGENTS.md에 뒷받침되지 않은 주장은 증거가 아니라고 명시하라고 권한다.
5. 비동기적으로 맡기고 맥락을 보존하며 사람의 검토를 집중한다
   - 에이전트 답변을 매번 기다리기보다 더 큰 일을 맡기고 요청을 모아서 처리하며, 두 시간 뒤 로그 확인이나 매일 아침 점검 같은 예약 실행을 활용하라고 한다.
   - 문맥 창 사용량을 손으로 추적하지 말라고 권하며, 문맥 압축으로 몇 개 메시지부터 수천 개 메시지까지 이어지는 대화를 다룰 수 있다고 설명한다.
   - Amp에서는 Git 커밋과 연결된 작업 대화가 과거 결정의 이유를 찾고 중복 작업을 피하게 해 주는 조직의 공유 기억이 된다.
   - 사람의 검토는 영향이 큰 파일과 변경에 집중하고, 처음부터 끝까지 시험하며, 작동 여부와 이해 가능성, 추후 변경 가능성을 살핀다. 로컬 자원 충돌은 여전히 실무상 장애물이다.
