## 📋 Quick Summary

### Building always-on agents
**Source:** Claude by Anthropic · **Category:** AI · **Link:** [Original](https://claude.com/ko/resources/articles/building-always-on-agents)
- Always-on agents are event-driven systems that sleep between short runs, retaining state across sessions rather than running continuously.
- The architecture centers on five primitives: an event inbox, timers, memory, permissions, and an outbox.
- Durable storage, a single active worker per inbox, retryable events, and carefully tuned user messaging make unattended operation more reliable.

---

## 📝 Detailed Notes

### 1. Building always-on agents

1. “Always-on” describes the experience, not continuous execution.
   - Agents spend most of their time asleep and wake when an event arrives.
   - Each run handles a task in a session containing messages and tool calls.
   - At the end of a run, the agent saves relevant state and returns to sleep.
2. An event inbox coordinates triggers and work.
   - Webhooks, scheduled tasks, and background jobs can all generate events.
   - A durable list, an HTTP handler, and a background worker form a simple inbox.
   - Track event status and deduplicate with source identifiers; a relational database can store events as rows.
   - Keep one worker active per inbox, retry pending events after failures, and batch related events when useful.
3. Timers make proactive work predictable.
   - Follow-ups are deadlines the agent sets; schedules are recurring user-defined tasks.
   - Store timers separately from ready-to-process inbox events.
   - A scheduler polls for due timers, marks follow-ups complete or advances schedules, then enqueues an event.
   - A custom background service or durable execution engine can run the scheduler.
4. Memory provides continuity across disconnected runs.
   - Store durable memory outside the worker, such as in a database or object store.
   - Save information that cannot be looked up elsewhere; use pointers for records already held in other systems.
   - Persist instructions, user preferences and corrections, prior messages, and ongoing task progress.
   - Keep initial context lean, use prompt caching to reduce cost, and save important details before compacting or restarting a long session.
5. Permissions and delivery shape safe, useful autonomy.
   - Credential proxies can inject secrets into outgoing requests without exposing them inside the agent environment.
   - Automated risk checks can block dangerous actions, while important decisions still need user review.
   - Deferred tool calls can pause a run for approval; the response returns as an inbox event and resumes the saved session.
   - An outbox and dispatcher can queue and deliver messages, support recovery, and control message pacing.
   - The full cycle connects inbox events, sessions, memory, permissions, timers, and outbound messages; evaluations help prevent both noisy over-messaging and missed updates.

## 📝 상세 정리

### 1. 항상 대기하는 에이전트 구축하기 (Building always-on agents)

1. ‘항상 대기’는 지속 실행이 아니라 사용자 경험을 가리킨다.
   - 에이전트는 대부분 잠들어 있다가 이벤트가 도착하면 깨어난다.
   - 각 실행(run)은 메시지와 도구 호출이 담긴 세션(session) 안에서 작업을 처리한다.
   - 실행이 끝나면 필요한 상태를 저장하고 다시 잠든다.
2. 이벤트 수신함(event inbox)이 트리거와 작업을 조율한다.
   - 웹훅(webhook), 예약 작업, 백그라운드 작업이 모두 이벤트를 만들 수 있다.
   - 지속성 있는 이벤트 목록, HTTP 처리기(handler), 백그라운드 작업자(worker)가 기본 수신함을 구성한다.
   - 이벤트 상태를 추적하고 출처의 고유 식별자로 중복을 제거한다. 관계형 데이터베이스에 이벤트를 행 단위로 저장할 수 있다.
   - 수신함마다 활성 작업자를 하나만 두고, 실패 후 대기 이벤트를 재시도하며, 필요하면 관련 이벤트를 묶어 처리한다.
3. 타이머(timers)는 능동적인 작업을 예측 가능하게 만든다.
   - 후속 확인은 에이전트가 정하는 기한이고, 일정은 사용자가 정하는 반복 작업이다.
   - 타이머는 처리 준비가 끝난 이벤트 수신함과 별도로 저장한다.
   - 스케줄러(scheduler)가 기한이 된 타이머를 확인하고, 후속 확인은 완료 처리하거나 반복 일정은 다음 시각으로 갱신한 뒤 이벤트를 등록한다.
   - 직접 만든 백그라운드 서비스나 지속 실행 엔진으로 스케줄러를 운영할 수 있다.
4. 메모리(memory)는 서로 분리된 실행 사이의 연속성을 제공한다.
   - 데이터베이스나 객체 저장소처럼 작업자 외부의 지속성 저장소에 메모리를 둔다.
   - 다른 곳에서 다시 찾을 수 없는 정보를 저장하고, 다른 시스템에 이미 있는 기록은 포인터로 참조한다.
   - 지침, 사용자 선호와 수정 사항, 이전 메시지, 진행 중인 작업의 경과를 보존한다.
   - 초기 문맥을 간결하게 유지하고 프롬프트 캐싱(prompt caching)으로 비용을 줄이며, 긴 세션을 요약하거나 재시작하기 전에 중요한 내용을 저장한다.
5. 권한과 전달 방식이 안전하고 유용한 자율성을 좌우한다.
   - 자격 증명 프록시(credential proxy)는 에이전트 환경에 비밀 정보를 노출하지 않고 외부 요청에 자격 증명을 삽입할 수 있다.
   - 자동 위험 검사가 위험한 행동을 막을 수 있지만, 중요한 결정에는 여전히 사용자의 검토가 필요하다.
   - 지연 도구 호출(deferred tool call)은 승인을 위해 실행을 멈출 수 있다. 응답은 수신함 이벤트로 돌아와 저장된 세션을 이어간다.
   - 발신함(outbox)과 전달기(dispatcher)는 메시지를 대기열에 넣고 전달하며, 오류 복구와 메시지 속도 조절을 지원한다.
   - 전체 흐름은 수신함 이벤트, 세션, 메모리, 권한, 타이머, 발신 메시지를 연결한다. 평가는 과도한 알림과 필요한 알림 누락을 모두 줄이는 데 도움이 된다.
